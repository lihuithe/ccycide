# 服务端测试

## 默认测试（无外部依赖）

```bash
cd server
npm ci
npm test          # vitest run；MySQL、真实 Redis 相关用例自动跳过
```

默认只用内存实现和 ioredis-mock，本机 Windows / macOS / Linux 都能跑，不需要 Docker。

## 真实依赖测试（MySQL 8.4 + Redis 7）

有 Docker 的机器上，用 `server/docker-compose.test.yml` 起真实的 MySQL 和 Redis，再用环境变量打开对应用例：

| 环境变量 | 作用 |
|---|---|
| `TEST_MYSQL_URL` | 打开 `test/mysql.test.ts`：迁移、全部仓储、sessions 分区维护、并发、MySQL 断开/冻结。库必须已存在，迁移由测试自动执行 |
| `TEST_REDIS_URL` | 打开 `test/redis-real.test.ts`：KV/Lua、在线状态、限流、会话计数、中继注册表、事件通道、总线、两个信令实例 + 中继的完整流程、Redis 断开/冻结/数据丢失。固定使用该实例的 db 9（`TEST_REDIS_DB` 可改），开始前会 `FLUSHDB`，不要指向有真实数据的实例 |

两个都设置时，全链路用例还会把真实 MySQL 与真实 Redis 一起接上。

### 在本机（有 Docker）

```bash
cd server
docker compose -f docker-compose.test.yml up -d --wait mysql redis    # 绑定 127.0.0.1:13306 / 16379
export TEST_MYSQL_URL=mysql://root:testroot@127.0.0.1:13306/rterm
export TEST_REDIS_URL=redis://:testredis@127.0.0.1:16379
npm test
docker compose -f docker-compose.test.yml down -v                      # 清理容器和数据卷
```

端口、密码可用 `TEST_MYSQL_PORT`、`TEST_REDIS_PORT`、`TEST_MYSQL_PASSWORD`、`TEST_REDIS_PASSWORD` 覆盖。项目名固定为 `rterm-test`，不会与 `deploy/` 的 `rterm` 栈冲突。

### 在服务器上（不装 node，用容器跑测试）

测试容器加入 compose 网络，直接用服务名访问：

```bash
cd server
docker compose -f docker-compose.test.yml up -d --wait mysql redis
docker run --rm -e NODE_ENV=development \
  --network rterm-test_default \
  -e TEST_MYSQL_URL=mysql://root:testroot@mysql:3306/rterm \
  -e TEST_REDIS_URL=redis://:testredis@redis:6379 \
  -v "$PWD":/app -w /app node:24-bookworm-slim \
  sh -c "npm ci --include=dev && npx vitest run"
docker compose -f docker-compose.test.yml down -v
```

- 镜像若设了 `NODE_ENV=production`，`npm ci` 会跳过 devDependencies，所以要 `NODE_ENV=development` 或 `--include=dev`。
- 4GB 内存的机器上 MySQL 已关闭 performance_schema，整套大约 2 分钟。
- 中国大陆服务器拉 `mysql:8.4` 很慢（带宽 1Mbps 时约 20 分钟），先拉好再跑。

### 故障注入用例怎么做的

Redis / MySQL 不可用的用例不需要 `docker stop` 权限：测试进程里起一个本地 TCP 代理（`test/tcp-proxy.ts`），让信令/中继的连接经过它。

- `cut()`：关闭监听并断开所有连接，对端看到连接被拒绝，等同容器停止。
- `freeze()`：连接保持但不转发，对端看到“无响应”，等同进程被挂起或网络黑洞。

真实停止容器的验证见下面的运行态步骤。

## 运行态验证（完整栈）

测试套件用 `rterm` 库（tsx 迁移，knex 迁移记录名是 `001_init.ts`），运行栈用 `rterm_stack` 库（编译后的 `dist/migrate.js`，记录名是 `001_init.js`），两者不能共用一个库，否则 knex 报 `The migration directory is corrupt, the following files are missing: 001_init.ts`。compose 已经在 MySQL 初始化时建好 `rterm_stack`（`server/docker/mysql-init.sql`）；如果 MySQL 数据卷是旧的，手工 `CREATE DATABASE rterm_stack`。

`docker-compose.test.yml` 的 `stack` profile 会再起 migrate + signal1 + signal2 + relay（镜像由 `server/Dockerfile` 构建）：

```bash
cd server
docker compose -f docker-compose.test.yml --profile stack up -d --build
# 客户端 demo（在同一网络的容器里，服务名访问）：
docker run --rm -e NODE_ENV=development --network rterm-test_default -v "$PWD":/app -w /app node:24-bookworm-slim \
  sh -c "npm ci --include=dev >/dev/null && npx tsx tools/rterm-client.ts demo --http http://signal1:8080"
# 跨实例：被控端连 signal2，主控端连 signal1
#   tools/rterm-client.ts host    --http http://signal2:8080 --identity /tmp/h.json
#   tools/rterm-client.ts connect <设备码> hello --http http://signal1:8080
docker compose -f docker-compose.test.yml --profile stack down -v
```

## 已知行为（Redis / MySQL 短暂不可用）

| 场景 | 行为 |
|---|---|
| Redis 断开 | 命令 3 秒内失败（`commandTimeout`，卡住不回包同样）；新的 `connect.request` 返回 `NO_RELAY`；注册返回 `503 UNAVAILABLE`；新的信令认证返回 `INTERNAL`（在线状态写不进去），客户端按退避重试；已建立的信令连接、中继会话继续工作；恢复后 ioredis 自动重连、总线自动重新订阅 |
| Redis 断开期间的总线消息 | Pub/Sub 不持久化，断开期间发布的 `connect.incoming` / `kick` 等丢失。`connect.request` 已经没有固定超时（被控端“连接确认”无限期等待），所以丢失的影响由下面几行的机制兜底，不会让主控请求一直挂着 |
| 向被控端投递 `connect.incoming` 失败 | 同一实例上连接已不在、跨实例 `PUBLISH` 抛错（Redis 不可用）、或 `PUBLISH` 返回 0 个订阅者（目标实例已退出）：主控立即收到 `connect.err UNAVAILABLE`，`reason=deliver_failed`，session 记为失败并清理计数 |
| 等待确认期间被控端掉线（连接断开、心跳超时、被同一设备新连接顶替、所在实例优雅退出） | 被控端所在实例清理时通过总线通知主控所在实例，主控收到 `connect.err UNAVAILABLE`。通知丢失（Redis 断开）或实例崩溃时，主控所在实例每 `pendingCheckMs`（默认 10 秒）检查一次被控端的在线状态，在线状态没了或换成了别的连接就以 `UNAVAILABLE` 结束；崩溃实例的在线状态最迟 90 秒过期。Redis 查询失败时本轮跳过，不会误杀 |
| 等待确认期间主控掉线（含所在实例退出或崩溃） | 主控所在实例清理时发 `connect.cancelled`（经总线）撤掉被控端的弹窗。通知丢失时，被控端所在实例每 10 秒检查：主控的在线状态没了/换了连接，或主控那边的等待项（`hp:` 会话集合）已不在，就撤掉弹窗。主控所在实例的清理写不进 Redis 时，在线状态最迟 90 秒后过期，弹窗随后被撤掉 |
| 被控端同意时答复发不到主控所在实例 | 被控端收到 `connect.cancelled`，不会一直等 `connect.go` |
| 等待确认的主控连接 | 不按“45 秒无消息”断开（用户可能很久才操作）；所有连接另有协议层 ping/pong 存活检测，半开连接两轮扫描（默认 30 秒）内被清理 |
| Redis 断开期间结束的中继会话 | 中继把 `ended` 事件（含字节数）放在本进程缓冲里，恢复后按序补发；中继进程在恢复前退出则缓冲丢失 |
| Redis 数据丢失（无持久化重启） | 在线状态由客户端下一次 `ping` 自动重新登记；中继节点在 10 秒内重新上报 |
| MySQL 断开或卡住 | 会话/安全事件写入进内存补写队列（单次写入 5 秒超时），恢复后按序补写；重复键等非暂时性错误丢弃而不堵队列；中继事件的应用同样进队列重试；设备/配置查询用缓存 |
