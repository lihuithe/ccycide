# 桌面端（Tauri 2 外壳）

`apps/desktop/src-tauri`，crate 名 `rterm-desktop`，已加入工作区。核心逻辑全部在 `rterm-core`（门面 `Core`），这里只做：命令转发、事件转发、终端输出通道、托盘、系统通知、插件装配、防睡眠。前端契约以 `apps/desktop/src/backend/types.ts` 为准，Rust 侧适配，前端未改。

## 启动流程

窗口先显示（`visible:false` 在 setup 里按 `--minimized` 决定是否显示），`Core::start` 放在后台任务，命令在核心就绪前会等待（最多 30 秒；启动失败则立即返回该错误）。核心启动后：同步 `closeToTray`、对齐开机自启状态、启动事件泵。核心库不初始化日志，由桌面端调用 `logging::init`（`<数据目录>/logs/`）。

## 命令（29 个，snake_case；参数 camelCase）

| 命令 | 说明 |
|---|---|
| `local_info` `refresh_temp_password` `set_fixed_password` | 直接对应 `Core`；`LocalInfo` 多出 `registered/lastError/lockedRemainingSecs/activeSessions`，前端忽略 |
| `accept_incoming` `reject_incoming` `disconnect_incoming` `disconnect_all_incoming` | 同名 |
| `list_known_hosts` `remove_known_host` | 同名 |
| `get_settings` `set_settings` | `set_settings` 把前端发来的对象**递归合并**到当前设置上再校验保存，前端没带的字段（`maxFileSize`、`maxTerminals`、`proxy` 等）不会被重置 |
| `connect` | 参数 `requestId`（前端生成）；对方设置了“连接确认”时**没有超时**，一直等到对方处理。额外可选参数 `acceptKeyChange`（对方公钥变化、用户确认后带 true 重连，前端暂未使用）。见下“connect 与 cancel_connect” |
| `cancel_connect` | `{requestId}`：取消还没连上的 connect（含“等待对方确认”）；被取消的 connect 以 `CANCELLED` 失败；requestId 不存在/已结束时静默成功 |
| `disconnect` `list_terms` `term_input` `term_submit` `term_resize` `term_ack` `close_term` `cancel_upload` `term_action` `command_list_req` | 同名；`fileId` 为十进制字符串，Rust 侧解析 |
| `open_term` `attach_term` | 带 `onOutput: Channel`；先登记通道再附着；`attach_term` 调 `Core::attach_term_from(.., Some(lastSeq))`，续传（小于核心已交付偏移时回退重发）完全由核心库负责，桌面端不再裁剪 |
| `upload_path` | 目录返回 `IS_DIRECTORY` |
| `upload_bytes` | 原始请求体 + 请求头 `x-session-id` / `x-name`（encodeURIComponent）/ `x-mime`；文件名只取最后一段 |
| `read_clipboard_files` | `clipboard-rs`；无文件返回 `[]`；剪贴板对象创建失败返回 `CLIPBOARD_UNAVAILABLE`；`file://` URI 会还原成本地路径 |
| `check_update` | Rust 侧检查更新：端点用核心库当前服务端地址 + `?kind=desktop&channel=<设置>&device_id=<设备码>`；返回 `{version,notes}` 或 `null` |

错误一律 `{code, message}`（`CoreError` 直接映射，`PEER_KEY_CHANGED` 等额外带 `data`）。

## 事件

全部经 `app.emit("core-event", …)`，载荷由 `Core::ui_event` 生成（`UiEvent`，与 `types.ts` 的 `CoreEvent` 一致）。

| 前端 type | 来源 |
|---|---|
| signalState incomingSession incomingClosed sessionState hostInfo termState termExit uploadProgress uploadDone uploadFailed actionCatalog appState appNotice commandList | 核心事件直接转换 |
| latency | 核心每 5 秒上报 |
| settingsChanged localInfoChanged | 核心在 `set_settings`、托盘“暂停被控”、临时密码刷新时发出 |
| sessionState 的 `attempt` / `retryInMs` | 核心的 `ReconnectInfo` 事件经 `ui_event()` 直接转成 `sessionState{state:'reconnecting', attempt, retryInMs}` |
| sessionState `awaitingApproval` | 见下“connect 与 cancel_connect”；connect 进行中时 `sessionId` 为空串并带 `requestId` |
| incomingClosed 的 `reason` | 桌面端合成：见下“来访确认” |
| `notice`、`upgradeRequired` | 前端契约之外，核心库新增，`ui_event()` 生成后**原样 emit**（前端当前忽略未知事件）；`upgradeRequired` 另会把窗口拉到前台，`notice` 记日志 |

除 `incomingClosed`、connect 进行中的 `sessionState` 外，其余事件都直接复用 `Core::ui_event()`，没有重复映射。

### 终端输出

`TermOutput` 不走事件。每个 `(sessionId, termId)` 一个 `Channel<InvokeResponseBody::Raw>`，帧 = `[8 字节 u64 大端 seq][数据]`。

- 同一终端连续输出在 Rust 侧每 8ms 或 64KB 合并一帧（超过 64KB 的单段会拆开）；偏移不连续时先刷出旧缓冲；
- 同一终端的 `termState/termExit/appState/appNotice/commandList` 事件发出前，先刷出该终端已合并的输出；
- 输出先于 Channel 登记到达（`open_term` 刚返回时）会暂存（每终端最多 4MB），登记时补发；
- 续传不在路由层处理：`attach_term` 传 `lastSeq` 给核心库，核心按它回退并重发 `[lastSeq, …)`（已实测：从中间偏移附着，帧偏移连续、字节一致，追平后附着不重发）；附着时丢弃登记前暂存的旧数据，`open_term` 则补发暂存；
- `term_ack` 同步转给 `Core::term_ack`，不等待核心启动；
- 终端退出、会话关闭时释放通道；`Channel::send` 失败（窗口销毁/页面刷新）时摘掉通道并转入暂存。

### connect 与 cancel_connect

`connect` 要等握手完成才返回，对方开了“连接确认”时可能等很久，所以前端传 `requestId`。核心库只在 `SessionState(Connecting/AwaitingApproval)` 事件里给会话 ID，桌面端用 `ConnectTable`（`state.rs`）把 requestId 与核心会话对上：

- `connect_gate` 把“开始连接 → 事件泵看到该会话的第一个状态事件”这一小段串行化（等待确认的漫长阶段不占用它），所以并发的 connect 不会绑错；
- connect 返回前，该会话的 `connecting` 不发，`awaitingApproval` 以 `{type:'sessionState', sessionId:'', requestId, state:'awaitingApproval'}` 发给前端；失败 connect 的后续 `closed` 事件不发（由命令的错误返回承载）；
- `cancel_connect` 在会话已绑定时调 `Core::cancel_connect`，未绑定（排队中或刚开始）时先记下，绑定时立刻取消；
- 其余事件（`hostInfo`、`ready` 等）照常带真实 sessionId 发出，由前端的“提早到达事件”缓冲处理。

## 来访确认

需要确认的来访**没有任何超时**：一直挂着直到用户处理、主控方取消，或被控端设置变化（核心库处理：`enabled` 关闭 → 全部拒绝，`requireConfirm` 关闭 → 全部放行）。可同时排多个。桌面端在新的待确认来访到达时把窗口拉到前台并按 `notifyOnConnect` 发系统通知，仅此而已。

`incomingClosed.reason` 由桌面端合成：用户在界面拒绝（`reject_incoming`，或对待确认项的 `disconnect_incoming` / `disconnect_all_incoming`）→ `rejected`；核心库发出 `Notice(INCOMING_CANCELLED)` 后紧随的 → `cancelled`；其余 → `closed`。用户同意后核心库不发 `IncomingClosed`（条目保留，随后 `incomingSession{pendingConfirm:false}`），所以不会出现 `accepted`；同意后握手失败则按 `closed`。

## 托盘、窗口、通知

- 托盘菜单：显示/隐藏窗口、状态行（设备码 · 在线/离线 · 暂停 · 连接数）、暂停被控（勾选，与设置同步）、断开全部连接、退出。左键单击切换窗口。有来访连接（已握手的）时图标换成带绿点的版本，提示文字同步。
- 关闭窗口：`app.closeToTray` 为 true 时隐藏到托盘；托盘创建失败（Linux 无托盘）时改为最小化。设置变化通过 `settingsChanged` 同步到 Rust。
- 自启动带 `--minimized`，窗口不显示，只在托盘；托盘不可用时仍显示。
- 单实例：再次启动只会把已运行实例的窗口拉到前台。
- 来访通知：需要确认的连接（`pendingConfirm`）到达时桌面端把窗口拉到前台，并按 `host.notifyOnConnect` 发系统通知；已连入的通知由前端 `controller.ts` 发（避免重复）。
- 睡眠唤醒：事件泵每 5 秒检测一次时间跳变，超过 20 秒视为睡眠唤醒，调用 `Core::network_changed()` 立即重连。
- `host.preventSleepWhenConnected`：核心库没有实现，桌面端做了（Windows `SetThreadExecutionState`；macOS `caffeinate`；Linux `systemd-inhibit`），仅在有已握手的来访连接时生效。
- 退出：托盘“退出”→ `app.exit` → `RunEvent::Exit` 里最多 3 秒执行 `Core::shutdown()`。

## 插件与权限（capabilities/default.json，仅 main 窗口）

插件：single-instance、autostart、updater、notification、clipboard-manager、dialog、window-state（不记可见性）、process、opener。

权限只授予前端实际用到的：`core:event:default`（监听 `core-event` 与窗口拖放事件）、`dialog:allow-open`、`notification:allow-is-permission-granted|request-permission|notify`、`clipboard-manager:allow-write-text`、`updater:allow-check|allow-download-and-install`、`process:allow-restart`、`autostart:allow-enable|disable|is-enabled`、`opener:allow-open-url`（只放行 `http://*`、`https://*`）。已实测：`window.close`、`fs.*`、`process.exit`、`file://` 链接均被拒绝。

拖放：窗口配置 `dragDropEnabled: true`，由 Tauri 接管系统拖放并经 `getCurrentWebview().onDragDropEvent` 给出本地路径（此时 WebView 自己的 HTML5 拖放不可用，这是 Tauri 的取舍）。

CSP：生产 `default-src 'self'`，`connect-src 'self' ipc: http://ipc.localhost`；开发另有 `devCsp` 放行 Vite 的 ws 和内联脚本。

## 更新

- `plugins.updater.endpoints` 是写死的占位 `https://api.example.com/v1/update/{{target}}/{{arch}}/{{current_version}}`；`pubkey` 是占位 `REPLACE_WITH_UPDATER_PUBKEY`（故意不是合法 base64，`createUpdaterArtifacts` 打包时会直接报错，防止带着占位发布）。
- 生成密钥：`cd apps/desktop && npx tauri signer generate -w ~/.tauri/rterm-updater.key`（或 `cargo tauri signer generate`）。命令输出的公钥填进 `tauri.conf.json` 的 `plugins.updater.pubkey`，私钥通过 `TAURI_SIGNING_PRIVATE_KEY`（+ `_PASSWORD`）提供给打包命令，私钥离线保管。
- 前端直接用 updater 插件的 JS `check()`，端点就是上面配置里的；插件 Builder 已默认附带请求头 `X-Device-Id`（从配置文件读设备 ID，首次启动没有）。**限制**：JS 路径无法按“更新通道”追加 `?channel=beta`；要支持 beta 需前端改走 `check_update`（Rust 版会带 channel）并另行处理下载安装，或发布时按通道分别打包端点。

## 随包资源

由“打包与 CI”侧的 `scripts/release-stage-resources.sh --target <三元组>` 生成（Windows 在 Git Bash 里运行）：

- `src-tauri/binaries/rterm-cli-<三元组>[.exe]` → 安装后是主程序同目录的 `rterm-cli[.exe]`，核心库 `default_rterm_cli` 会自动找到；开发时 `cargo build -p rterm-cli` 到同一个 target 目录即可；也可用环境变量 `RTERM_CLI` 指定。
- `src-tauri/resources/conpty.dll`、`OpenConsole.exe` → 安装后与主程序同目录。启动时检查，缺失记 warn 并降级到系统 ConPTY（开发构建只记 info）。

打包命令（在 `apps/desktop` 下）：

```
npx tauri build --config src-tauri/tauri.bundle.conf.json --config src-tauri/tauri.bundle.windows.conf.json
```

## 构建与运行

```
cd apps/desktop && npm ci
# 开发（Vite 在 1420）
$env:CARGO_TARGET_DIR="<仓库根目录>\target-tauri"   # 可选，避免和别人抢 target 锁
npx tauri dev                    # 加 --no-watch 可避免别的 agent 改核心库时反复重启
# 检查
cargo clippy -p rterm-desktop --no-deps --all-targets -- -D warnings   # --no-deps：rterm-core 自带的 clippy 告警不属于本 crate
cargo test -p rterm-desktop
npm run build                    # 前端
npx tauri build --debug --no-bundle   # 不打安装包的发布形态（内嵌 dist，生产 CSP）
```

常用环境变量：`RTERM_API_URL`（服务端地址）、`RTERM_DATA_DIR`（数据目录，同机多实例/测试）、`RTERM_NO_KEYRING=1`（机密存文件）、`RTERM_CLI`。

调试 WebView：`npx tauri dev --config src-tauri/tauri.devtools.conf.json` 会在 9222 打开 CDP，可用 `Runtime.evaluate` 直接 `window.__TAURI_INTERNALS__.invoke(...)` 调命令、`Page.captureScreenshot` 截图。

Windows 静态链接 CRT（`+crt-static`）需要在仓库根的 `.cargo/config.toml` 里配置，属于打包侧，这里没有设置。

## 已验证（本机 Windows 10，WebView2 157，Node 24，本地 `dev:all` 服务端 + `rterm-cli host` 做被控端）

- `cargo clippy --no-deps -D warnings`、`cargo test`（10 个单元测试，含 ConnectTable）、`npm run build`、`tauri build --debug --no-bundle`、`tauri build --debug --bundles nsis`（NSIS 安装包 14.6MB；静默安装后目录里有 `rterm-desktop.exe`、`rterm-cli.exe`、`conpty.dll`、`OpenConsole.exe`，启动日志“已找到随包的 ConPTY”）。
- `tauri dev` 与生产形态（嵌入 dist）都能起窗口，界面显示设备码、临时密码、在线状态。
- 通过界面连接 `rterm-cli host`：打开终端、看到 PowerShell 提示符、输入并执行 `1..3000` 的大输出（流控 ack 正常）、状态栏延迟 3ms。
- 命令：`upload_path`（文件成功、目录 `IS_DIRECTORY`、不存在的文件报错）、`upload_bytes`（原始请求体 + 中文文件名，被控端 inbox 里文件名正确）、`read_clipboard_files`（文件列表/纯文本返回 `[]`）、`set_settings` 合并保留字段、`check_update`（204 返回 null）、`cancel_upload` 非法 id 报 `BAD_REQUEST`、不存在的会话报 `NO_SUCH_SESSION`。
- 来访：用 `examples/probe_controller` 连入本机——`incomingSession`、`localInfoChanged` 事件到达前端；托盘图标出现绿点，断开后恢复。
- 连接确认（本机 dev 服务端与测试服务器 `<API 域名>`（真实值见本机 `docs/测试服务器凭据.local.md`）各验证一遍）：开启 `requireConfirm` 后请求挂起 40 秒以上仍未被拒绝，之后在界面点“同意”才连上（探针用时 44.7 秒）；两个探针同时连入，两个请求排队并列；点“拒绝”→ 探针收到 `REJECTED`，前端 `incomingClosed.reason = rejected`；探针调用 `cancel_connect` → 弹窗撤掉，前端收到 `notice` + `incomingClosed.reason = cancelled`，探针的 connect 返回 `CANCELLED`。
- 桌面端作主控：`connect{requestId}` 等待 `rterm-cli host`（开了确认）时收到 `sessionState{sessionId:'', requestId, state:'awaitingApproval'}`；3 秒后 `cancel_connect` → connect 以 `CANCELLED` 失败，且没有多余的 closed 事件；对未知 requestId 取消静默成功；另一次等待 36 秒后 `rterm-cli accept`，connect 成功返回会话 ID。
- 续传：`attach_term` 传中间偏移 `lastSeq`，新通道首帧偏移正好等于它、与已有输出字节一致、偏移连续；`lastSeq` 等于已收总量时不重发。
- 测试服务器冒烟：桌面端（真实界面）连 `rterm-cli host`，执行命令看到输出；桌面端作被控端开确认后探针连入、挂起 36 秒、取消，事件序列正确。
- 托盘（真实右键菜单、鼠标点击）：菜单项和状态行、“暂停被控”（设置变更并同步勾选与 `settingsChanged`）、“断开全部连接”（对端收到 kicked）、“退出”（进程退出）；左键单击托盘显示窗口。
- 关闭窗口 → 进程保留、窗口隐藏；再次启动 exe → 单实例唤起窗口；`--minimized` 启动窗口不显示。
- 拖放：用另一个进程发起真实 OLE 文件拖放到窗口，`tauri://drag-enter` 与 `drag-drop` 事件带出本地绝对路径。
- 权限：插件命令可用，未授权命令（`window.close`、`fs`、`process.exit`、`file://` 链接）被拒。

## 未验证 / 已知限制

- 系统通知：API 调用成功、无报错，但本机没有看到 Windows toast（开发构建的 AUMID 问题或系统通知设置，未能判定）；macOS/Linux 未测。
- 开机自启：`is_enabled` 可读，没有实际写入注册表测试（避免改动用户环境）；Rust 侧启动对齐逻辑未跑到“需要变更”的分支。
- updater：配置与 `check` 调用链通，没有真实发布 + 签名包的下载安装验证（需先有 `app_releases` 记录和真实公钥）；JS 路径不带 `?channel=`。
- macOS / Linux：没有编译和运行（`power.rs` 的 `caffeinate` / `systemd-inhibit` 分支、托盘降级路径都未实测）；Wayland 剪贴板失败路径未测。
- Claude Code 相关（`term_action`、`command_list_req`、状态回传 hook）只做了命令转发，没有在真实 Claude Code 上验证。
- 重连续传在桌面端层面的行为（断网重连、睡眠唤醒检测）没有做破坏性测试。
