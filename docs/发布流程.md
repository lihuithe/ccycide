# RTerm 发布流程

对应《实现方案》第 12、13 章，《开发指南》T33（三平台打包和签名）、T34（自动更新）。

文中的 `<OWNER>/<REPO>` 是 GitHub 仓库的占位，仓库建好后替换。

---

## 1. 总览

```
打 tag v0.2.0 ──▶ .github/workflows/release.yml
                    │
                    ├─ prepare        校验 tag 与各处版本号一致，建草稿 Release
                    ├─ desktop ×6     Windows x64 / x64 离线 WebView2 / ARM64，macOS 通用，Linux x64 / arm64
                    ├─ cli ×6         Linux x64/arm64 musl 静态，Windows x64/arm64，macOS x64/arm64
                    ├─ server-image   rterm-server 镜像 → ghcr.io（amd64 + arm64）
                    ├─ publish        ⏸ 等人审批 → 签命令行包、生成 SHA256SUMS.txt、公开 Release
                    └─ update-server  （可选）向更新服务器登记，默认 5% 灰度
```

每次 push / PR 跑 `.github/workflows/ci.yml`：Rust 三平台 fmt / clippy / test，前端 tsc / eslint / vitest / build，服务端 tsc / vitest，服务端 MySQL 8.4 + Redis 7 集成，依赖审计（不阻塞）。本机一键等价命令：`scripts/ci-local.ps1`。

### 产物

| 产物 | 文件 | 说明 |
|---|---|---|
| Windows 桌面 x64 / ARM64 | `RTerm_<ver>_x64-setup.exe`、`RTerm_<ver>_arm64-setup.exe` | NSIS，按用户安装，内嵌 WebView2 引导安装器。updater 直接使用这个文件，旁边有 `.sig` |
| Windows 离线包 | `RTerm_<ver>_x64-offline-setup.exe` | 带完整 WebView2 运行库，给 LTSC / Server / 无网络环境；不参与自动更新 |
| macOS 桌面 | `RTerm_<ver>_universal.dmg`、`RTerm.app.tar.gz` + `.sig` | 通用二进制；`.app.tar.gz` 是 updater 用的 |
| Linux 桌面 | `.deb`、`.rpm`、`.AppImage` + `.AppImage.sig` | x86_64 与 aarch64，在 Ubuntu 22.04 上构建 |
| 命令行版 | `rterm-cli-<ver>-<target>.tar.gz` / `.zip` + `.sig` | Linux 为 musl 静态；Windows 压缩包内带 `conpty.dll`、`OpenConsole.exe` |
| 校验和 | `SHA256SUMS.txt` | 覆盖以上全部文件 |
| 更新清单 | `latest.json` | tauri-action 生成，作为 GitHub 侧备份；客户端实际走自己的 `/v1/update` |
| 服务端镜像 | `ghcr.io/<owner>/rterm-server:<ver>`、`:latest`、`:<主>.<次>` | 预发布版本只有 `:<ver>` |

## 2. 需要提前办好的账号与证书

证书审核要时间，**项目早期就申请**。

| 项目 | 用途 | 费用 / 周期 | 说明 |
|---|---|---|---|
| GitHub 仓库 | 放代码、跑 Actions、托管 Release 与 GHCR 镜像 | — | arm64 Linux runner（`ubuntu-22.04-arm`）仅对公开仓库免费；私有仓库要用自托管 runner，或删掉 release.yml 里的 `linux-arm64` 项 |
| Apple Developer Program | macOS 签名 + 公证 | 99 美元 / 年；个人几天，公司（需邓白氏编码）1–3 周 | 需要 Developer ID Application 证书（不是 Developer ID Installer，也不是 Mac App Store 证书） |
| Windows 代码签名 | 消除 SmartScreen 警告、杀软误报 | 见下 | 二选一 |
| updater 签名密钥 | 校验更新包 | 免费 | 自己生成，见第 3 节 |
| 一台服务端 | 更新服务器、信令、中继 | — | 见《部署指南》 |
| Linux | 无需签名 | — | 提供 `SHA256SUMS.txt`；deb / rpm 仓库的 GPG 签名暂不做 |

**Windows 代码签名的两条路**

| 方案 | 特点 | CI 集成 |
|---|---|---|
| Azure Trusted Signing（微软托管，证书短期轮换） | 约 10 美元 / 月；需要 Azure 订阅，并通过主体身份验证（对开通地区与主体类型有限制，申请前先在 Azure 门户确认；服务名称以后可能变动）。通常能较快获得 SmartScreen 信誉 | `WINDOWS_SIGN_MODE=azure`，已在 release.yml 里接好 |
| 传统 OV / EV 证书 | OV 要积累下载量才消除警告；EV 立即生效但更贵。2023 年起新发的证书私钥必须放在硬件里，**不能导出成 PFX** | `WINDOWS_SIGN_MODE=pfx` 只适用于仍可导出的证书。硬件令牌 / 云 HSM（DigiCert KeyLocker、SSL.com eSigner 等）要走厂商的命令行，由 Tauri 配置的 `signCommand` 调用，需另行接入 |

建议：能开通就选 Azure Trusted Signing，CI 最省事。

## 3. updater 密钥

### 生成

```bash
cd apps/desktop
npm run tauri -- signer generate -w ~/.tauri/rterm-updater.key
```

输出两个文件：`rterm-updater.key`（私钥）与 `rterm-updater.key.pub`（公钥）。设一个密码。

### 放哪里

| 内容 | 位置 |
|---|---|
| 公钥（`.key.pub` 全文，一整串 base64） | `apps/desktop/src-tauri/tauri.conf.json` → `plugins.updater.pubkey`（目前是占位 `REPLACE_WITH_UPDATER_PUBKEY`） |
| 同一个公钥 | `rterm-cli` 的 `update` 子命令内置，用来验证命令行包 |
| 私钥（`.key` 全文） | GitHub secret `TAURI_SIGNING_PRIVATE_KEY` |
| 私钥密码 | GitHub secret `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` |

### 保管

- 私钥离线备份至少两份，放在不同介质、不同地点；密码另存。
- **私钥或密码丢失后，已安装的客户端永远无法再自动更新**（它们只信任旧公钥），只能让用户手动重装带新公钥的版本。
- 不要换密钥来"顺便轮换"；确实要换时，先发一个同时认新旧公钥的过渡版本（需要客户端支持，目前 Tauri updater 只接受一个公钥，所以实际无法平滑轮换）。

### release.yml 的占位保护

`prepare` 任务会检查 `tauri.conf.json` 里不含 `REPLACE_WITH` 和 `api.example.com`，没改占位值就不会发布。

## 4. Secrets、Variables 与 Environments 清单

在仓库 Settings → Secrets and variables → Actions 里添加。`GITHUB_TOKEN` 由 Actions 自动提供。

### Secrets

| 名称 | 用途 | 什么时候需要 |
|---|---|---|
| `TAURI_SIGNING_PRIVATE_KEY` | updater 签名私钥全文 | 必需 |
| `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` | 上述私钥的密码 | 必需 |
| `APPLE_CERTIFICATE` | Developer ID Application 证书（.p12）的 base64 | 签 macOS |
| `APPLE_CERTIFICATE_PASSWORD` | 导出 .p12 时设的密码 | 签 macOS |
| `APPLE_SIGNING_IDENTITY` | 证书全名，如 `Developer ID Application: 公司名 (TEAMID)` | 签 macOS |
| `APPLE_ID` | 开发者账号的 Apple ID 邮箱 | 公证 |
| `APPLE_PASSWORD` | 该账号的**应用专用密码**（appleid.apple.com 生成，不是登录密码） | 公证 |
| `APPLE_TEAM_ID` | 10 位团队 ID | 公证 |
| `WINDOWS_CERTIFICATE` | PFX 证书的 base64 | `WINDOWS_SIGN_MODE=pfx` |
| `WINDOWS_CERTIFICATE_PASSWORD` | PFX 密码 | 同上 |
| `AZURE_CLIENT_ID`、`AZURE_CLIENT_SECRET`、`AZURE_TENANT_ID` | 有 Trusted Signing 签名权限的应用注册 | `WINDOWS_SIGN_MODE=azure` |
| `ADMIN_TOKEN` | 更新服务器管理接口令牌（即服务端 `.env` 里的 `ADMIN_TOKEN`） | `UPDATE_SERVER_MODE=direct` |
| `UPDATE_SSH_KEY` | 登记用的 SSH 私钥 | `UPDATE_SERVER_MODE=ssh` |
| `UPDATE_SSH_KNOWN_HOSTS` | 服务器主机公钥（本机执行 `ssh-keyscan -t ed25519 服务器` 得到） | 同上 |

没配置 Apple secrets 时 macOS 包仍会构建，只是没有签名和公证，用户打开会被 Gatekeeper 拦下；Windows 同理（不设 `WINDOWS_SIGN_MODE` 就不签）。想让缺签名直接失败，把对应变量改成必需并在 workflow 里加检查。

### Variables

| 名称 | 取值 | 说明 |
|---|---|---|
| `WINDOWS_SIGN_MODE` | `pfx` / `azure` / 不设 | Windows 签名方式 |
| `AZURE_TS_ENDPOINT`、`AZURE_TS_ACCOUNT`、`AZURE_TS_PROFILE` | Trusted Signing 的区域端点、账户名、证书配置名 | `azure` 方式 |
| `UPDATE_SERVER_MODE` | `direct` / `ssh` / 不设 | 不设则 `update-server` 任务整个跳过 |
| `UPDATE_SERVER_URL` | 管理接口能访问到的地址，如 `http://10.0.0.5:8080` | `direct`。管理接口在公网入口返回 404（deploy/Caddyfile），所以这个地址必须是内网 / VPN / 自托管 runner 能到的 |
| `UPDATE_SSH_TARGET` | `deploy@服务器`（用户需能执行 `docker compose exec`） | `ssh` |
| `UPDATE_DEPLOY_DIR` | 服务器上 compose 所在目录，默认 `/opt/rterm/deploy` | `ssh` |
| `ROLLOUT_PERCENT` | 首次灰度比例，默认 5 | 可选 |

### Environments

| 名称 | 设置 | 作用 |
|---|---|---|
| `release` | Required reviewers 勾上负责人 | `publish` 任务停在这里等审批。审批前草稿 Release 里的包可以下载到干净机器验证 |
| `update-server` | 限定 `v*` tag；可再加审批 | 保护 `ADMIN_TOKEN`、SSH 私钥 |

ssh 方式的 SSH 用户在 docker 组里，等同于服务器 root 权限：用专用账号、专用密钥，只用于发布。

## 5. 版本号规则

- 语义化版本：`MAJOR.MINOR.PATCH[-预发布标识]`，tag 为 `v` + 版本号，如 `v0.2.0`、`v0.3.0-beta.1`。
- 唯一来源是根 `Cargo.toml` 的 `[workspace.package] version`；`crates/*` 与 `src-tauri` 用 `version.workspace = true`。
- 前端 `package.json`、服务端 `package.json`、各 `package-lock.json`、`Cargo.lock`、`tauri.conf.json`（若写了 `version`）必须与它相同。
- 带 `-` 的是预发布：GitHub Release 标为 prerelease，更新服务器登记到 `beta` 通道，镜像不更新 `latest`。服务端比较版本时预发布小于同号正式版（`0.3.0-beta.1 < 0.3.0`）。
- 版本字符串不超过 32 个字符（`app_releases.version` 列的长度）。
- 当前不构建 MSI。若以后加 MSI，WiX 要求预发布标识必须是纯数字（`0.3.0-1`）。
- 校验与修改用 `scripts/release-prepare.ps1`（Windows）或 `scripts/release-prepare.sh`，行为一致：

```powershell
scripts/release-prepare.ps1                    # 检查全部一致
scripts/release-prepare.ps1 -Expect v0.2.0     # 检查并要求等于 0.2.0（CI 的 prepare 任务就这样用）
scripts/release-prepare.ps1 -Set 0.2.0         # 批量改成 0.2.0 并复查
scripts/release-prepare.ps1 -Set 0.2.0 -DryRun
```

## 6. 发布步骤

### 6.1 第一次发布前的演练

1. 在一个私有测试仓库（或本仓库的一个分支）把 `WINDOWS_SIGN_MODE`、Apple secrets 都留空，只配 `TAURI_SIGNING_PRIVATE_KEY`，推一个 `v0.0.1-rc.1`，确认六个桌面任务、六个命令行任务、镜像任务都能跑通。
2. 把 `tauri.conf.json` 里的 pubkey 和 endpoints 换成真实值。
3. 逐项配好第 4 节的 secrets，再推 `v0.0.2-rc.1` 验证签名与公证。

### 6.2 正式发布

1. `main` 上 CI 全绿。
2. 改版本号并提交：
   ```powershell
   scripts/release-prepare.ps1 -Set 0.2.0
   git add -A; git commit -m "release: v0.2.0"
   ```
3. 打标签并推送：
   ```bash
   git tag v0.2.0
   git push origin main v0.2.0
   ```
4. 在 Actions 里看 `Release` 工作流。`desktop` / `cli` / `server-image` 都成功后会停在 `publish`，等待审批。
5. **审批前做安装验证**：从草稿 Release 下载各平台安装包，在干净的虚拟机上装、启动、完成一次连接（T33 的验证标准）。检查项：
   - Windows：`signtool verify /pa` 验证安装目录下每个 exe / dll；安装目录里有 `conpty.dll` 和 `OpenConsole.exe`；SmartScreen 的表现。
   - macOS：下载后用浏览器下载的副本（带隔离属性）双击能直接打开；`spctl -a -vv` 显示 Notarized Developer ID。
   - Linux：`sha256sum -c`；deb / AppImage 能启动。
   命令见 `scripts/release-sign-notes.md`。
6. 审批 `publish`：命令行包被签名并上传，生成 `SHA256SUMS.txt`，Release 转为公开。
7. 如果开启了 `UPDATE_SERVER_MODE`，`update-server` 任务自动把更新包登记到更新服务器，灰度 5%。没开启就在能连到管理接口的机器上手动登记：
   ```bash
   # 经 SSH 在服务器的 signal 容器里发请求（不需要开端口）
   export RTERM_ADMIN_SSH=deploy@your-server
   gh release download v0.2.0 -D assets          # 需要 .sig 文件，所以要整个目录下载
   bash scripts/release-admin.sh publish --version 0.2.0 --assets assets \
     --base-url https://github.com/<OWNER>/<REPO>/releases/download/v0.2.0 --rollout 5
   ```
8. 服务端有改动时，按第 10 节更新服务器上的镜像。

### 6.3 灰度放量

客户端按设备标识哈希取模决定是否收到更新（`rolloutBucket`，见 `server/src/api/update.ts`）。

```bash
bash scripts/release-admin.sh list                         # 查看各记录与灰度比例
bash scripts/release-admin.sh rollout-version 0.2.0 25     # 观察 24 小时无异常后放量
bash scripts/release-admin.sh rollout-version 0.2.0 100
```

观察指标：崩溃率、连接成功率、用户反馈、`/metrics`。

### 6.4 重跑

某个任务失败（常见是公证超时）：在 Actions 里 Re-run failed jobs。需要整体重来时，手动运行 `Release` 工作流并填入同一个 tag，草稿 Release 会被复用，同名资产会被覆盖。

## 7. 回滚

| 情况 | 做法 |
|---|---|
| 新版本有问题，还在灰度中 | `release-admin.sh revoke-version 0.2.0`。未收到更新的客户端不会再收到；已更新的保持不变 |
| 已更新的客户端要回到好版本 | Tauri updater 只升不降。发布 `0.2.1`（内容 = 旧版本代码 + 必要修复），放量即可 |
| 误撤回 | `release-admin.sh restore ID` |
| GitHub Release 本身有问题 | 把 Release 改回草稿或删除其资产。更新服务器记录一并撤回，否则客户端下载会 404 |
| 服务端镜像有问题 | `.env` 里的 `IMAGE_TAG` 改回上一个版本，`docker compose up -d`。数据库迁移不回滚，所以迁移必须向前兼容（见《部署指南》7.4） |

## 8. 强制升级（`min_app_version`）

低于 `min_app_version` 的客户端在连接信令时收到 `force_upgrade` 通知，客户端据此要求升级后才能继续使用（`server/src/signal/handlers.ts`）。

```bash
bash scripts/release-admin.sh min-version 0.2.0       # 低于 0.2.0 的客户端被强制升级
bash scripts/release-admin.sh clear-min-version       # 取消
```

使用规则：

1. 只用于协议不兼容、严重安全漏洞这类情况。
2. **先把目标版本放量到 100%，再设置 `min_app_version`。** 否则被强制升级的用户在更新服务器上拿不到新版本，等于把人锁在外面。
3. 不要把它设得高于已发布的最高版本。
4. 它存在数据库的下发配置里，优先级高于服务端环境变量 `MIN_APP_VERSION`；`clear-min-version` 后回落到环境变量的值。
5. 与协议版本（`MIN_PROTO_VER`）是两件事：后者由服务端按协议握手拒绝，前者是对用户的升级要求。

## 9. 签名、公证、SmartScreen 常见坑

### Windows

- 所有要运行的 exe / dll 都应带有效签名：安装包、主程序、`rterm-cli.exe`。`conpty.dll` 与 `OpenConsole.exe` 来自微软官方 NuGet 包，已有微软签名，**不要重新签**。Tauri 打包时是否给 externalBin 签名要在首次发布演练时用 `signtool verify /pa` 实测确认，没签就在 `signCommand` 里补。
- 签了名不等于没有 SmartScreen 警告：OV 证书和新的 EV / Trusted Signing 身份都需要积累信誉。保持签名主体、文件名、安装包形式稳定；可向微软提交文件分析（https://www.microsoft.com/wdsi/filesubmission）。
- 时间戳必不可少，否则证书过期后签名失效。workflow 里用 `http://timestamp.digicert.com`。
- 远程控制类软件容易被杀软误报。每次大版本发布后，把安装包提交给主流厂商（火绒、360、腾讯、卡巴斯基、Defender）做白名单申请。
- ARM64 包在 x64 的 runner 上交叉编译，无法在 CI 里运行测试，必须在 ARM64 机器（如 Surface、Parallels 虚拟机）上手工验证。
- 静态链接 CRT（`+crt-static`）已在 workflow 里设置；本机打包时同样要设置 `RUSTFLAGS`，否则用户机器要装 VC++ 运行库。
- NSIS 按用户安装（`installMode: currentUser`），不需要管理员权限。

### macOS

- `APPLE_PASSWORD` 必须是应用专用密码，不是 Apple ID 登录密码；账号需开启双重认证。
- 公证失败最常见原因：内嵌的二进制（sidecar `rterm-cli`）没有用同一证书、带时间戳、开启强化运行时签名；`.app` 里含 `get-task-allow` 权限。公证日志用 `xcrun notarytool log <提交ID>` 查看。
- 第一次公证可能等几小时，之后通常几分钟。工作流超时 90 分钟，超时后 Re-run 即可。
- 通用二进制的 sidecar 必须是 `lipo` 合并后的，`release-stage-resources.sh --target universal-apple-darwin` 已处理。
- 验证要用"浏览器下载"的文件（带 `com.apple.quarantine`），本机 `scp` 过来的不会触发 Gatekeeper，测不出问题。
- 证书过期（Developer ID 5 年，账号年费 1 年）会导致新版无法签名；已安装的旧版不受影响，但已公证的包仍有效。

### Linux

- 在 Ubuntu 22.04 构建，目标系统需 glibc ≥ 2.35 与 WebKitGTK 4.1。更老的发行版请用命令行版（musl 静态）。
- AppImage 在部分最小化系统需要 `libfuse2`；可用 `--appimage-extract-and-run`。
- 命令行 musl 版依赖的 crate（如 `keyring` 的 Secret Service 后端）在 musl 上是否可用，需要在首次发布演练时验证；不可用则回退到文件存储。

### 通用

- GitHub 的 Release 资产 URL 对私有仓库需要鉴权，客户端无法直接下载。更新服务器登记的是 `releases/download/...` 地址，所以**私有仓库不能直接用这个地址**，要改成自己的下载域名（把资产同步到对象存储 / CDN，并把 `--base-url` 指过去）。
- 国内用户访问 GitHub 下载较慢，正式运营后建议把资产镜像到 CDN，`--base-url` 指向 CDN。

## 10. Docker 镜像发布与 `deploy/` 的衔接

### 发布

`server-image` 任务把 `server/Dockerfile` 构建为 `linux/amd64` + `linux/arm64`，推到 `ghcr.io/<owner>/rterm-server`（owner 全小写）：

| 标签 | 何时更新 |
|---|---|
| `<ver>`，如 `0.2.0` | 每次发布 |
| `latest`、`<主>.<次>`，如 `0.2` | 仅正式版 |

首次推送后，包默认是私有的。要么在 GitHub 的 Packages 页把可见性改为 public，要么在服务器上 `docker login ghcr.io`（令牌只需 `read:packages`）。

### 部署

`deploy/docker-compose.ghcr.yml` 是覆盖文件，把 `migrate` / `signal` / `relay` 的镜像换成 GHCR 的，并去掉本地构建：

```bash
cd /opt/rterm/deploy
# .env 里设置：
#   RTERM_IMAGE=ghcr.io/<owner>/rterm-server
#   IMAGE_TAG=0.2.0
docker compose -f docker-compose.yml -f docker-compose.ghcr.yml pull
./backup.sh                                                        # 先备份（《部署指南》第 8 节）
docker compose -f docker-compose.yml -f docker-compose.ghcr.yml up -d
docker compose ps
```

- 不想每次写两个 `-f`：在 `.env` 里加 `COMPOSE_FILE=docker-compose.yml:docker-compose.ghcr.yml`。
- 回滚：`IMAGE_TAG` 改回上一版本，再 `up -d`。
- 中继节点：`docker compose -f docker-compose.relay.yml -f docker-compose.ghcr.yml up -d relay`。
- 需要 Docker Compose ≥ 2.24（覆盖文件用了 `!reset`）。
- 服务器在国内拉 GHCR 可能很慢或失败。退路是仍按《部署指南》7.3 在服务器上 `docker compose build`，或把镜像推到阿里云 / 腾讯云镜像仓库再拉取。
- 客户端发布和服务端发布共用同一个 tag，但可以只部署其中之一：服务端没变化时不必升级服务器，客户端没变化时不必登记更新。

## 11. 对 Tauri 配置与门面的要求清单

Tauri 的配置由桌面端负责，下面是发布流水线对它的要求，括号内是写作时的现状。

### tauri.conf.json 及其附属配置

| 要求 | 现状 |
|---|---|
| `version` 缺省，或与 `Cargo.toml` 工作区版本一致（`release-prepare` 会检查） | 一致 |
| `plugins.updater.pubkey` 换成真实公钥；`endpoints` 换成真实域名，格式 `https://<API_DOMAIN>/v1/update/{{target}}/{{arch}}/{{current_version}}` | 占位，**发布前必须改**，否则 prepare 任务会拦下 |
| `bundle.createUpdaterArtifacts: true`，放在 `tauri.bundle.conf.json`，打包时用 `--config` 合并（CI 已这样传） | 满足 |
| `bundle.externalBin: ["binaries/rterm-cli"]`，同样只放在 `tauri.bundle.conf.json`（日常 `tauri dev` 不需要这个文件，避免没有 sidecar 时报错） | 满足 |
| Windows 资源：`tauri.bundle.windows.conf.json` 里 `resources/conpty.dll` → `conpty.dll`、`resources/OpenConsole.exe` → `OpenConsole.exe`，安装后与主程序同目录；程序启动时校验两个文件存在（T33 要点） | 配置满足；启动校验见下 |
| `bundle.windows.webviewInstallMode: embedBootstrapper`；NSIS `installMode: currentUser` | 满足。离线包由 CI 用 `--config` 临时覆盖为 `offlineInstaller` |
| 签名信息不写进仓库：`bundle.windows.certificateThumbprint` / `signCommand`、`bundle.macOS.signingIdentity` 都留空，由 CI 注入（Windows 通过 `--config` 临时文件，macOS 通过 `APPLE_*` 环境变量） | 满足 |
| `bundle.macOS.minimumSystemVersion: "11.0"`；需要时通过 `bundle.macOS.entitlements` 指定权限文件，强化运行时在签名时默认开启 | 未设置，**建议补上** |
| `bundle.targets` 含 `nsis`、`deb`、`rpm`、`appimage`、`dmg`。CI 用 `--bundles` 显式指定了每个平台要出的包（macOS 为 `app,dmg`，因为 updater 需要 `.app.tar.gz`），所以 targets 只影响本机打包 | 满足 |
| `app.security.csp` 不影响 updater（插件在 Rust 侧联网） | 无需处理 |
| `capabilities` 含 `updater:allow-check`、`updater:allow-download-and-install`、`process:allow-restart` | 满足 |
| 工作区 `Cargo.toml` 的 `members` 包含 `apps/desktop/src-tauri`，CI 的 fmt / clippy / test 才会覆盖到它 | 满足 |
| `.gitignore` 忽略 `src-tauri/binaries/`、`src-tauri/resources/` | 满足 |

### 流水线提供给打包的文件

由 `scripts/release-stage-resources.sh --target <三元组>` 在打包前生成，路径是两边约定的接口：

| 路径 | 内容 |
|---|---|
| `apps/desktop/src-tauri/binaries/rterm-cli-<三元组>[.exe]` | 编译好的 `rterm-cli`。macOS 的 `universal-apple-darwin` 是 `lipo` 合并后的 |
| `apps/desktop/src-tauri/resources/conpty.dll`、`OpenConsole.exe` | 仅 Windows 目标。来自 NuGet 包 `Microsoft.Windows.Console.ConPTY` 1.24.261001001，脚本里固定了 SHA256，x64 与 ARM64 各取对应架构 |

本机打包同样先跑这个脚本（Windows 在 Git Bash 里）。`--stub` 生成空占位文件，只用于不需要真内容的检查。

### 对桌面端 / 门面（`rterm-core`）代码的要求

| 要求 | 原因 |
|---|---|
| 向服务端注册 / 连接时上报 `app_version`（取自 Cargo 版本） | `min_app_version` 强制升级依赖它 |
| updater 请求带上设备标识：`updater_builder().header("X-Device-Id", …)` 或在 endpoint 加 `?device_id=` | 灰度按设备哈希分桶；不带则退回按 IP 哈希，同一出口 IP 的用户会被分到同一个桶 |
| 选择 beta 通道时 endpoint 加 `?channel=beta` | 服务端按通道过滤，默认 `stable` |
| Windows 启动时确认 `conpty.dll`、`OpenConsole.exe` 在可执行文件同目录；缺失时记日志并降级到系统 ConPTY | 开发指南 T33 |
| 有活跃会话或运行中的终端时，下载完成后不自动重启，提示用户 | 实现方案 12.4 |
| `rterm-cli --version` 输出工作区版本；`rterm-cli update` 请求 `/v1/update/{os}/{arch}/{ver}?kind=cli`，下载压缩包后用内置公钥验证 `.sig`（与 updater 同一把密钥、同一格式）再替换自身 | 命令行版更新 |
| `rterm-cli` 在 Windows 上同样从 exe 同目录加载 `conpty.dll` | 命令行压缩包里已带这两个文件 |
| `rterm-cli` 能在 `*-unknown-linux-musl` 目标上编译并运行 | CI 用 `cargo zigbuild` 构建 |

## 12. 本机脚本

| 脚本 | 作用 |
|---|---|
| `scripts/ci-local.ps1` | 本机跑 CI 同款检查。`-WhatIf` 只打印命令并检查路径；`-NoTest` 只跑静态检查；`-Skip rust,desktop,server` 跳过某组；`-Install` 先 `npm ci`；`-Integration` 加跑 MySQL 集成（需要 `TEST_MYSQL_URL`） |
| `scripts/release-prepare.ps1` / `.sh` | 版本号一致性检查与批量修改 |
| `scripts/release-stage-resources.sh` | 生成 externalBin 与 ConPTY 资源 |
| `scripts/release-admin.sh` | 更新服务器管理：登记、列表、灰度、撤回、强制升级 |
| `scripts/release-checksums.sh` | 生成 `SHA256SUMS.txt` |
| `scripts/release-sign-notes.md` | 签名与验证命令速查 |

仓库里的 `*.sh` 必须是 LF 换行。Windows 上若开启了 `core.autocrlf`，请在仓库根加 `.gitattributes`：`*.sh text eol=lf`。

## 13. 首次发布时需要实测确认的点

这些无法在本机验证，第一次演练时逐项过：

1. `tauri build --config <文件>` 的相对路径解析，以及多个 `--config` 的合并顺序。
2. Windows 上 sidecar `rterm-cli.exe` 是否被签名。
3. macOS 公证是否通过（sidecar 与主程序同一证书）。
4. `ubuntu-22.04-arm` runner 是否可用，AppImage 在 arm64 上能否生成。
5. musl 目标上依赖库能否编译。
6. 离线 WebView2 安装包的资产上传（走 GitHub 上传接口，文件约 170 MB）。
7. 更新服务器登记：`release-admin.sh publish` 对文件名的识别规则取决于 Tauri 的产物命名（`*-setup.exe`、`*.app.tar.gz`、`*.AppImage`）；`productName` 改动不影响，后缀规则变了才需要改脚本。
